## 三 第3项 派生题不能绕过来源公开分发限制

### 1 用户刚刚明确确认的规则

用户已确认：**派生获得独立编辑和版本管理权，不自动获得公开分发权。派生题保留来源的公开分发限制；即使内容不变或稍作修改，也不能通过派生绕过原作者授权。**

因此：

- A仅把Q/v1定向共享给B，没有允许公开分发。
- B可以按既有规则派生自己的F/v1、维护后续版本并用于自己的问卷。
- B不能仅凭“F属于自己”就把它放进公开模板；公开时仍需满足来源作者的分发授权。
- 这项确认不改变已有派生题的编辑、版本维护、自用及统计归属；派生题仍独立统计，不与原题合并。

### 2 当前设计缺口

现设计一方面要求他人题目必须有公开分发授权，另一方面允许原样派生为自己的题，又把自有题视为隐式可公开。组合后会形成“定向共享→派生→自有题→免授权公开”的绕行路径。

不要通过禁止所有派生、禁止正常编辑、强制内容改动比例或相似度检测来解决。所有权与来源分发限制必须分别表达。

### 3 修订要求

1. 在需求决策中登记这条用户新确认规则，并同步权限矩阵；不能继续笼统写“自有题一律可公开”。区分没有受限来源的原创题与带来源约束的自有派生题。
2. 明确来源限制如何经过多级派生和后续正式版本持续保留。A→B→C时，不能只检查C的owner或直接父来源而漏掉仍有效的上游限制；恢复、另建版本或再次派生不能清除来源约束。
3. 给出尽量简单的可落地授权检查方案，说明要检查的具体来源版本、作者、实际模板发布者和当前授权。作者只能授予自己控制的权利，不能替上游作者授权；授权不自动转授。
4. 对多级来源检查的具体粒度给出明确技术推荐及理由。可以选择逐层检查未解除的来源分发义务或等价方案，但不能弱化“派生不自动取得来源公开权”这一确认；不得把详细字段选择写成用户亲自指定。
5. 来源来自服务端既有不可变正式版与派生事实，不能信任客户端自报原创、清空origin、替换sourceVersionId或伪造授权。正常API没有去掉受限来源的操作。
6. 说明缺失、损坏、循环或无法完整核验的派生链如何处理：不能跳过不明环节然后默认可公开；给出稳定错误及修复路径。不要仅因迁移题标记legacyImport就认定它一定是他人派生，区分已有明确来源与确实没有记录的来源。
7. 同步模板创建、上架、可用性/预览、选用及公开授权接口的检查条件。凡当前设计要求验证公开分发资格的地方，必须覆盖来源义务，不能只在首次发布时检查。
8. 当前TemplateBinding只有单个publicGrantId。评估它是否足以表达多级来源；如果不足，调整设计字段/证明结构、白名单、索引、示例和hash规范，说明哪些证明固定保存、哪些状态每次实时检查。不要保留互相矛盾的新旧字段。
9. 同步并发设计：如需核查上游授权，相关题目门闩也纳入确定的锁顺序和同事务检查，避免源作者撤销授权与模板分发并发时遗漏保护。保留P2-003的模板accessFence/revision分离与完整历史回执。
10. 更新公开DTO时不要暴露内部授权证明、源问卷管理信息或其他不必要字段；内部需要遍历授权不意味着公开全部链路细节。
11. 检查模板选用者的权限矩阵与正文是否一致：既有规则允许针对自己模板生成实例派生，不应在矩阵中误写为必须另有整题共享；但派生后的公开仍受本轮新规则约束。
12. S04同版重复实例限制、S05公开授权具体粒度、S06公开撤权影响，仍按现有状态标注。此次只确认派生继承来源分发限制，不代表用户顺带确认所有暂定项；对本轮必须细化的技术取舍明确说明。

### 4 至少补充以下设计验收场景 全部标未执行

- B获A定向共享后原样派生，没有公开授权，发布模板被拒。
- B稍改内容、保存新版、恢复或再派生，不能清除来源约束。
- 只有定向共享或模板内固定版本使用权，仍不足以公开派生内容。
- 获得所需明确公开授权后，允许按授权范围公开。

## 四 第4项 引用状态必须对应具体题目版本

### 1 当前设计缺口

P2-U01当前Usage只有versions:[{versionId,version}]，isDraft/isCurrent/onlyHistorical放在问卷层。如果同卷草稿使用v2、当前发布使用v1、历史还用过v1，前端无法从单条响应知道每个版本的具体使用状态。

### 2 推荐响应结构

保留“一份问卷一行”，在每个version项中明确状态。例如他人的问卷：

```json
{
  "surveyNumber": "usage_B_independent",
  "username": "student_demo",
  "versions": [
    {"versionId": "720000000000000000000002", "version": 2,
     "isDraft": true, "isCurrent": false, "hasHistorical": false},
    {"versionId": "720000000000000000000001", "version": 1,
     "isDraft": false, "isCurrent": true, "hasHistorical": true}
  ],
  "isDraft": true,
  "isCurrent": true,
  "onlyHistorical": false
}
```

可采用等价命名，但必须将状态和具体题目版本直接关联，并同步所有契约与例子。这个示例是建议的目标，不是已实现接口响应。

### 3 修订要求

1. 精确定义版本级isDraft、isCurrent、hasHistorical；历史指非当前的已发布问卷版本引用，不是“只要曾发布就算历史”。同一个题目版本可同时有多种状态。
2. 问卷级isDraft为各版本isDraft的OR，isCurrent同理；onlyHistorical在无draft、无current且存在历史使用时为true。全部通过后端事实计算，不接受客户端状态。
3. 同步数据库文档中的查询算法、API Usage本人/他人DTO、U01文字和JSON示例、api-contracts.json、页面说明及测试计划。
4. 明确versionId过滤的含义：建议先限制匹配题目版本，再计算该次结果中的版本级与问卷级状态；不能选v1后仍混入v2的草稿状态。若有其他合理语义，必须明确、统一并给例子。
5. 继续按surveyId聚合一行，多个历史问卷发布快照不能把同一问卷计成多份；每题版本在versions内也去重。version项给稳定排序，不返回无界的历史发布号数组。
6. 保持权限边界：他人的问卷仍只显示用户名、独立usageNumber编号、题目版本及状态，不新增内部surveyId、标题、分享链接、答卷或统计；本人保留已有标题和管理入口。
7. 派生关系列表仍独立，不能将其并入原题的直接引用。

### 4 至少补充以下未执行用例和静态样例

- 同卷草稿用v2、当前发布用v1、历史也用v1：版本级状态准确，问卷只一行。
- 同题同版同时出现在草稿、当前和若干历史快照：一个版本项，三个状态均正确，不重复计数。
- 仅历史使用：问卷onlyHistorical=true，相关版本hasHistorical=true。
- versionId过滤后，没有混入其他版本状态；无匹配不返回空壳问卷行。
- 多问卷、多版本及分页仍稳定，用户名/编号白名单不扩大。
